== Constraint model
Constraints live in `Sketch` (`include/sketchcad/constraint.h`, `sketch.h`), so Document snapshots,
Undo/Redo and command rollback cover the constraint set together with the geometry.

* A constraint has a stable ID from the same per-document allocator as entities; IDs are never reused
  and never collide with entity IDs.
* `Constraint { id, kind, first, second, target, internal }`. `second` is 0 for unary kinds.
  `target` is used only by `kFix`, `internal` only by circle–circle tangency.
* `add_constraint(kind, first, second = 0)` validates kinds and references (table below) and returns the ID,
  or `nullopt` without changing the sketch or the allocator.
  It only records the relation; it does not move geometry. Solving is a separate step.
* `constraint(id)` and `constraints()` query; `erase(id)` removes a constraint.
* An entity referenced by a constraint cannot be erased (no implicit cascade, consistent with C01);
  callers erase the constraint first. `constraints_of(entity)` lists the constraints that reference it.
* `Sketch` equality compares entities and constraints, not the allocator watermark;
  Document no-op detection uses it, so adding a constraint is an undoable change.

=== Supported kinds and pairs
[cols="1,2,2,2"]
|===
|Kind |References |Residuals (hard) |Notes

|`kCoincident` |point, point (distinct) |Δx, Δy [mm] |
|`kHorizontal` |line; or point, point |y~end~ − y~start~ [mm] |
|`kVertical` |line; or point, point |x~end~ − x~start~ [mm] |
|`kParallel` |line, line (distinct) |cross(d~1~, d~2~) / (\|d~1~\| \|d~2~\|) |Direction-agnostic.
|`kPerpendicular` |line, line (distinct) |dot(d~1~, d~2~) / (\|d~1~\| \|d~2~\|) |
|`kTangent` |line, circle/arc (either order, stored line first) |distance(center, infinite line) − r [mm] |Arcs are treated as their full circle.
|`kTangent` |circle/arc, circle/arc (distinct) |\|c~1~c~2~\| − (r~1~ + r~2~) external, \|c~1~c~2~\| − \|r~1~ − r~2~\| internal [mm] |`internal` is chosen at creation from the closer of the two configurations and stored.
|`kEqual` |line, line (distinct) |\|d~1~\| − \|d~2~\| [mm] |Equal length.
|`kEqual` |circle/arc, circle/arc (distinct) |r~1~ − r~2~ [mm] |Equal radius.
|`kFix` |point |x − x~0~, y − y~0~ [mm] |Target is the position at creation.
|===

Everything else is rejected: unknown or zero IDs, wrong entity types, the same entity twice,
a `second` for `kFix`, a missing `second` where a pair is required.
Construction geometry may be constrained like normal geometry.

== Solver
`SolveResult solve(Sketch&)` (`include/sketchcad/solver.h`, `src/constraint_solver.cpp`).

* Variables are the positions of points and the radii of circles/arcs that constraints reference
  (directly, or through a line's endpoints and a curve's center). Everything else is left untouched.
  Arc angles are not variables in S01.
* All constraints are hard residuals in one Ceres problem (Levenberg–Marquardt, dense QR);
  radii have a positive lower bound, so a solution never needs a non-positive radius.
* No stabilization or drag residuals are added in S01. Under-constrained sketches move as little as the solver needs;
  the exact position of free DOF is not a contract.
* The solve is transactional: it works on copied parameters and writes back only on `kSolved`.
  On any other status the sketch is unchanged.

=== Tolerance policy
Convergence does not prove satisfaction: after every solve each hard residual is re-evaluated in double precision.

* Length residuals (mm): |r| ≤ 1e-7 mm.
* Angular residuals (parallel, perpendicular; sine/cosine): |r| ≤ 1e-9.
* Solved positions and radii must be finite, radii strictly positive.

=== Status
[cols="1,3"]
|===
|`kSolved` |All hard residuals within tolerance; solved values written back. An empty constraint set is solved without change.
|`kInvalidInput` |A residual or its derivative is undefined for the input geometry before solving: a line no longer than the
length tolerance in a parallel, perpendicular, equal-length or tangent constraint, or concentric centres in a circle–circle tangency
(internal or external). Nothing is solved.
|`kUnsatisfied` |Ceres converged to a minimum with at least one hard residual out of tolerance: the constraints
contradict each other (locally). `violated` lists those constraint IDs.
|`kNumericalFailure` |Ceres failed, hit its iteration limit with residuals out of tolerance, or produced non-finite values.
Distinct from `kUnsatisfied`: it does not claim a conflict.
|`kDegenerate` |The constraints are satisfied only by collapsing geometry: a line that was longer than the length
tolerance becomes no longer than it, or a circle/arc radius becomes no larger than it (for example horizontal plus vertical
on one line). Nothing is written back. Geometry already degenerate before solving is `kInvalidInput` instead.
`violated` is empty; the collapsed entities are not constraints.
|===

`SolveResult { status, violated, max_length_residual, max_angle_residual }`.
Minimal conflict sets are not promised (S01-DIAG).

=== Document integration
`solver_step()` returns a `Document` commit step that solves the working copy and rejects the command
unless the status is `kSolved`. Installed with `Document::set_commit_step`, a command that adds a conflicting
constraint leaves geometry, constraints, history and allocator-visible state as before (rollback includes the constraint set).
The app does not install the solver yet; that comes with the constraint UI (U02).

== Acceptance / test cases
Core GoogleTest (`constraint_test` for the model, `constraint_solver_test` for solving):

* Model: valid pairs per kind accepted; wrong types, unknown IDs, duplicates of the same entity and wrong arity rejected
  atomically (sketch and next ID unchanged); constraint IDs are unique with entities and not reused;
  constrained entities cannot be erased until the constraint is; tangent order is normalized; `internal` is chosen
  from the closer configuration; snapshot assignment and equality include constraints.
* Solver, per kind: a positive scenario (violated geometry becomes satisfied) and a conflict scenario built with `kFix`
  (or equal radii plus tangency) that returns `kUnsatisfied` and leaves the sketch unchanged.
* Every solved scenario is checked with an independent residual oracle written in the test, not with solver code.
* Mixed geometry: a rectangle with horizontal/vertical sides, an equal side pair, a fixed corner and a circle tangent
  to a side and of equal radius to an arc solves together.
* Degenerate inputs: zero-length line in parallel/perpendicular/equal → `kInvalidInput`; already satisfied constraints
  leave values unchanged; geometry not referenced by constraints is never touched.
* Document: with `solver_step()` installed, adding a conflicting constraint fails and leaves sketch, constraints and
  history unchanged; a satisfiable one is one undo step and Undo restores both geometry and constraint set.

All existing CTest checks stay green. Desktop-only; nothing here is claimed for Android.

== Implementation notes
* Ceres rejects the same parameter block twice in one residual (lines sharing a point), so every constraint is a
  `DynamicAutoDiffCostFunction` over deduplicated point/radius blocks.
* If all hard residuals are already within tolerance, Ceres is not run and nothing is written back.
* Solver options: Levenberg–Marquardt, dense QR, at most 200 iterations, function/gradient/parameter tolerances 1e-16.

== Degenerate solutions (issue #29)
Added after user testing of U02: horizontal followed by vertical on one line was accepted and collapsed the line to a point.
`kDegenerate` rejects such solutions.
Before rejecting, the solver retries once with the lengths of the collapsed lines and the radii of the collapsed curves held
at their input values (temporary, not stored, no IDs allocated in the result). If that solves, its geometry is used:
vertical applied to an exactly horizontal line rotates the line and keeps its length instead of collapsing it.
If the retry fails, the status is `kDegenerate`. Diagnostics report a degenerate candidate as `kUnknown` with `kInvalidGeometry`.
Acceptance: vertical on an exactly horizontal line solves with its length kept; horizontal + vertical on one line, coincident on both endpoints of one line, and a fixed-centre circle tangent to a
fixed line through that centre (radius driven to its lower bound) are each `kDegenerate` and leave the sketch unchanged; with `solver_step()`
the command is rolled back; points made coincident on purpose (two free points) still solve.
